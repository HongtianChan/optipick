# 讨论总结：样本提取系统算法优化（分层 + 启发式搜索）

## 一、讨论背景与目标
首先讨论了一个事情：
公式
设 k = ⌈n/2⌉（向上取整），则本质不同的位置数 = k(k+1)/2（三角形数）
n	k	本质不同位置数
2	1	1
3	2	3
4	2	3
5	3	6
6	3	6
7	4	10
直观理解
正方形有 8 种对称操作（4 个旋转 + 4 个翻转），这些操作会把很多位置"等价化"。
你可以把格子想象成只看左上角的三角形区域：
4×4 的情况：A B . .B C . .. . . .. . . .只需要看 A, B, C 三个位置，其他都是它们的"镜像/旋转版本"
这个三角形区域刚好是 1 + 2 + ... + k 个格子，就是三角形数。
数学背景
这来自群论的 Burnside 引理，用来数在对称群作用下的等价类数量。正方形的对称群叫 D4（二面体群）。

大规模（C(n,k) > 100）：贪心算法近似解

在你补充之前，我先从算法优化角度分析一下这个项目当前的几个可改进点：
1. 贪心算法效率问题
当前贪心每轮都要遍历所有 k 组计算新覆盖数：
algorithm.js
Lines 89-132
function greedySetCover(nSamples, k, j, s, atLeast = 1) {  // ...  while (covered.size < allJCombinations.length) {    for (const kGroup of allKGroups) {  // 每轮全量遍历      // ...    }  }}
这导致复杂度是 O(选择组数 × 总组数 × j组合数)，规模大时会很慢。
2. 回溯剪枝可以更强
当前只有"当前组数 ≥ 已知最优则停"的简单剪枝，可以加入下界估计来更早剪枝。
3. 没有利用问题的数学结构
集合覆盖问题有很多成熟的优化方法：ILP（整数线性规划）、分支定界、列生成等。

## 二、优化点在代码中的位置

以下均以 **`cli/src/algorithm.js`** 为准（`api/algorithm.js` 已与之一致）。

### 1. 覆盖预计算（为贪心加速 + 供启发式用）

| 位置 | 说明 |
|------|------|
| **第 87–98 行** `buildCoverageIndexes(...)` | **新增函数**。预计算每个 k 组覆盖的 j 组合**下标**列表，避免在贪心/回溯中重复调用 `coversRequirement`。 |
| **第 104 行** | 贪心入口处调用 `buildCoverageIndexes`，得到 `coverageIndexes`。 |
| **第 114–118 行** | 每轮用 `coverageIndexes[g]` 的下标集合与 `covered` 做差集计数（`!covered.has(jIdx)`），不再对每个 (k 组, j 组合) 调用 `coversRequirement`。 |
| **第 130 行** | 用 `coverageIndexes[bestIdx]` 更新 `covered`，避免再次遍历全部 j 组合。 |

### 2. 贪心内部的小优化

| 位置 | 说明 |
|------|------|
| **第 107 行** `selectedKey = new Set()` | 用「组的字符串 key」做 O(1) 判重，替代 `selected.some(sel => JSON.stringify(sel) === ...)`。 |
| **第 115 行** | 判重改为 `selectedKey.has(allKGroups[g].join(','))`。 |
| **第 130 行** | 选中后 `selectedKey.add(bestGroup.join(','))`。 |

### 3. 分层：贪心后的冗余组移除

| 位置 | 说明 |
|------|------|
| **第 137–160 行** `removeRedundantGroups(...)` | **新增函数**。对已选组逐个检查：若该组覆盖的所有 j 组合都已被其他已选组覆盖，则从解中删除该组（分层里的「精修」层）。 |
| **第 232–234 行**（`solveOptimalSamples` 贪心分支） | 贪心得到 `result` 后，调用 `removeRedundantGroups(result, allJ, j, s, atLeast)`，用返回值作为最终解。 |

### 4. 回溯的启发式与剪枝

| 位置 | 说明 |
|------|------|
| **第 166 行** | 回溯内调用 `buildCoverageIndexes`，得到 `coverageIndexes`，供排序和下界用。 |
| **第 169–172 行** | **启发式排序**：按 `coverageIndexes[i].length` 降序重排 `allKGroups` 和对应的 `reorderedCoverage`，覆盖多的组优先被尝试。 |
| **第 174 行** | `maxSingleCover = max(各组覆盖数, 1)`，用于下界计算。 |
| **第 176–179 行** | **上界（分层）**：回溯前先跑贪心，用 `greedySolution.length` 初始化 `bestCount` 和 `bestSolution`，剪枝更紧。 |
| **第 190–193 行** | **下界剪枝**：`uncovered = 未覆盖 j 数`，`lb = ceil(uncovered / maxSingleCover)`；若 `selected.length + lb >= bestCount` 则直接 return，不再往下搜。 |
| **第 198 行** | 扩展当前覆盖时用 `reorderedCoverage[startIdx]` 直接加 j 下标，不再对每个 j 调用 `coversRequirement`。 |

## 三、优化手段与效果小结

| 类别 | 手段 | 作用 |
|------|------|------|
| **分层** | 贪心 → 冗余移除 | 贪心解后处理，删除冗余组，减少组数。 |
| **分层** | 回溯前先跑贪心作上界 | 回溯起始 `bestCount` 更小，剪枝更早。 |
| **启发式** | 覆盖预计算 `buildCoverageIndexes` | 贪心、回溯共用，少算覆盖关系，加速。 |
| **启发式** | k 组按覆盖数降序排列 | 回溯优先进「覆盖多」的分支，更快得到好解。 |
| **启发式** | 下界剪枝 `lb = ceil(uncovered/maxSingleCover)` | 提前剪掉不可能优于当前最优的分支。 |
| **实现细节** | 贪心用 `selectedKey` Set 判重 | O(1) 判重，避免数组+JSON 比较。 |

- **回溯**：仍为精确算法，仅加入启发式顺序与剪枝，不改变解的正确性。  
- **贪心**：近似算法，多了一层冗余移除，通常能得到更少组数。
